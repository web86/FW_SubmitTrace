# FW Submit Trace

**Временный диагностический набор для MODX Revolution 2 и SendIt 2.8.x.**

Помогает выяснить, почему форма не отправляется, SendIt не успевает инициализироваться, запрос уходит обычной навигацией вместо AJAX или поведение отличается между ручной проверкой и автоматическим тестом (например, в FormWatch).

Инструмент **наблюдает**, а не исправляет сайт: не нажимает кнопки, не вызывает `submit()`, не отменяет события, не подменяет обработчики и не читает содержимое полей, CAPTCHA, токены SendIt или тела ответов. Для отправки диагностических событий используется отдельный запрос к тому же сайту.

> **Важно:** это временный инструмент разработчика, **не** постоянно работающий мониторинг. Используйте его только на своём сайте или с разрешения владельца, затем отключите.

## Что входит

| Файл | Назначение |
|---|---|
| [`fw-submit-trace.js`](fw-submit-trace.js) | Пассивно наблюдает загрузку SendIt, формы и отправку в браузере |
| [`FWDebugCollector.plugin.php`](FWDebugCollector.plugin.php) | MODX-плагин, принимает события браузера и пишет их в журнал |
| [`FWLifecycleTrace.plugin.php`](FWLifecycleTrace.plugin.php) | Необязательный MODX-плагин для трассировки серверных событий запроса |
| [`tools/compare-traces.mjs`](tools/compare-traces.mjs) | Сравнивает две трассировки из `error.log` (Node.js 18+) |
| [`tools/compare-traces.test.mjs`](tools/compare-traces.test.mjs) | Самотест анализатора |

Поддерживается установка на **любом домене**. По умолчанию JS отслеживает формы с `data-si-form` или `data-si-preset` (в том числе внутри модальных окон). Адреса страниц и пресеты не зашиты в код.

## Быстрый старт

### 1. Создайте временный токен

Нужны **48 шестнадцатеричных символов**. Например, в терминале с PHP:

```bash
php -r 'echo bin2hex(random_bytes(24)), PHP_EOL;'
```

Сохраните результат для следующих шагов. Не используйте опубликованные в примерах или ранее применявшиеся токены.

### 2. Добавьте настройки MODX

В менеджере MODX откройте **Система → Настройки системы** и создайте:

| Ключ | Пример значения | Для чего |
|---|---|---|
| `fw_debug_enabled` | `1` | Включает диагностические плагины |
| `fw_debug_token` | **твой новый 48-символьный hex-токен** | Совпадает с токеном в JS |
| `fw_debug_origin` | `https://example.com` | Разрешённый Origin; укажите **реальный адрес проверяемого сайта** |
| `fw_debug_paths` | `/contact,/ru/contact` | Список URL-путей для серверных HTTP- и lifecycle-логов |

- `fw_debug_origin` необязателен, если `site_url` в MODX уже содержит правильный origin (схема + домен + порт), но явная настройка надёжнее.
- `fw_debug_paths` — разделённые запятыми **пути без домена**. Для URL `https://example.com/ru/contact?x=1` путь — `/ru/contact`. Завершающий `/` игнорируется. Эта настройка нужна для серверной трассировки, а не для выбора формы в JS.
- В примерах `example.com` — условное имя. Замените его своим доменом.

### 3. Установите плагины

Создайте два плагина в MODX, вставив код соответствующих файлов (в редакторе MODX при необходимости уберите открывающий `<?php`):

**FWDebugCollector** — обязательный, событие:

```text
OnMODXInit
```

**FWLifecycleTrace** — необязательный, полезен при проблемах с Localizator, перенаправлениями и жизненным циклом страницы. Подпишите его на события:

```text
OnMODXInit
OnHandleRequest
OnPageNotFound
OnWebPageInit
OnLoadWebDocument
```

Проверьте, что плагины включены. Очистите кэш MODX.

### 4. Подключите JavaScript

Скопируйте `fw-submit-trace.js` на сайт, например в `/assets/js/`.

Добавьте **синхронно в `<head>`, до JS SendIt**, без `async` или `defer`:

```html
<script>
window.FW_TRACE_CONFIG = {
  token: 'PASTE_YOUR_NEW_48_HEX_TOKEN_HERE',
  paths: ['/contact', '/ru/contact']
};
</script>
<script src="/assets/js/fw-submit-trace.js?v=1"></script>
```

Укажите **тот же** токен, что в `fw_debug_token`. После изменения файла увеличивайте `?v=`, чтобы не использовать старую версию из браузерного кэша.

`paths` в JS **необязателен**: если его убрать, инструмент работает на любой HTTPS-странице, где подключён. Для диагностики конкретных страниц оставьте список.

По умолчанию выбираются:

```css
form[data-si-form], form[data-si-preset]
```

Для одной формы можно задать `selector`:

```js
window.FW_TRACE_CONFIG = {
  token: 'PASTE_YOUR_NEW_48_HEX_TOKEN_HERE',
  paths: ['/contact'],
  selector: 'form[data-si-form="ContactForm"]'
};
```

Имя пресета автоматически читается из `data-si-preset` **той формы, которая отправляется**. Для формы в модальном окне наблюдатель не открывает окно самостоятельно: его должен открыть пользователь или тестовый сценарий.

### 5. Выполните проверку

1. Откройте выбранную страницу по **HTTPS**, лучше в новом приватном окне.
2. Проверьте в консоли браузера сообщения `[FW TRACE]`.
3. Отправьте проверяемую форму вручную или запустите разрешённый тест FormWatch.
4. Посмотрите журнал MODX, обычно `core/cache/logs/error.log`.

В журнале могут появиться:

```text
[FW TRACE JS]   событие из браузера
[FW TRACE HTTP] связанный HTTP-запрос, если он прошёл через MODX
[FW LIFECYCLE] событие MODX для выбранного пути
```

Успешный ответ на `POST /fw-debug/collect` — **HTTP 204**. Приёмник принимает **одно событие за запрос**. События отправляются через `sendBeacon` после завершения SendIt, через 8 секунд после submit без `si:send:finish` или при уходе со страницы. Доставка не гарантирована, а порядок записей в журнале может отличаться от порядка генерации.

Для просмотра в консоли сервера:

```bash
grep '\[FW TRACE' core/cache/logs/error.log | tail -n 120
grep '\[FW LIFECYCLE' core/cache/logs/error.log | tail -n 120
```

## Как читать диагностические события

| Сигнал | Что означает |
|---|---|
| `boot`, `dom_ready`, `window_load` | Фазы загрузки страницы |
| `si_init` | Поймано событие `si:init` |
| `sendit_ready` | Впервые обнаружен `window.SendIt.Sending` |
| `asset_probe` | Наблюдение за `index.js` и загрузкой JS SendIt |
| `module_probe` | Пассивные метрики отдельных модулей SendIt на этапах `load` и `submit` |
| `navigation_probe` | Метрики загрузки HTML-документа |
| `submit_capture`, `submit_bubble`, `submit_microtask` | Состояние нативного события отправки; отслеживается `defaultPrevented` |
| `si_send_before`, `si_send_after`, `si_send_success`, `si_send_error`, `si_send_finish` | Наблюдаемые события SendIt |
| `script_error`, `runtime_error`, `promise_rejection` | Ошибки загрузки скрипта, исполнения JS и необработанных Promise |
| `pagehide` | Уход со страницы |

Опрос готовности SendIt происходит раз в **250 мс**, максимум **30 секунд**. `module_probe` фиксирует метрики Resource Timing, не делает дополнительных запросов.

**Как не ошибиться с выводами:**

- `http_status=0`, `index_resource=false` или `observed=false` означают **«не наблюдалось»**, а не доказанную ошибку загрузки.
- `HTTP 200` не подтверждает выполнение JS; `index_module=false` сам по себе тоже не ошибка.
- `[FW TRACE HTTP]` для `/assets/components/sendit/action.php` может отсутствовать: этот PHP-файл способен обрабатывать запрос вне MODX.
- `submit_capture` без `si_send_success` не доказывает ни успешную, ни неуспешную отправку.
- `si_msg_token_err` вместе с отсутствием `OnWebPageInit` **может** указывать на проблему инициализации токена при внутреннем forward локализованной страницы. Сначала сопоставьте серверные события и отсутствие `X-SITOKEN`: это не универсальный диагноз.
- Наличие формы в HTML не означает, что автоматический тест может взаимодействовать с ней: модальное окно может оставаться закрытым.

## Сравнение удачной и неудачной проверки

Скопируйте журнал MODX в файл `error.log` на компьютер с **Node.js 18+**. Сторонние npm-зависимости не нужны.

Найти трассировки (32-символьные `trace` ID):

```bash
node tools/compare-traces.mjs error.log
```

Сравнить две:

```bash
node tools/compare-traces.mjs error.log TRACE_SUCCESS TRACE_FAILURE
```

Запустить тест анализатора:

```bash
node tools/compare-traces.test.mjs
```

Сравнение показывает времена загрузки, события и состояние модулей. Сверяйте его с ответом SendIt и результатом проверки формы; это **инструмент наблюдения, а не автоматический вердикт**.

## Если ничего не записывается

| Симптом | Что проверить |
|---|---|
| Нет `[FW TRACE]` в браузере | Скрипт реально загружен **до SendIt**, HTTPS, правильный `paths`, 48 hex-символов в `token`, отсутствие ошибок JS |
| `POST /fw-debug/collect` возвращает 403 | `fw_debug_enabled`, совпадение токенов, `fw_debug_origin`, Same-Origin, cookie `fw_trace` |
| `POST /fw-debug/collect` возвращает 404 | Достигает ли запрос MODX и исполняется ли `FWDebugCollector` на `OnMODXInit`; проверьте маршрутизацию/rewrite |
| Возвращается 400 | Версия JS/плагина, разрешённое имя события, корректный ID трассировки |
| Нет `[FW LIFECYCLE]` | Привязки событий и `fw_debug_paths`; проверяемый путь действительно указан |
| Форма не находится в автоматическом тесте | Фактический URL после переходов, CSS-селектор, необходимость открыть модальное окно |
| Не видно `[FW TRACE HTTP]` для AJAX | Проверьте Network: AJAX endpoint может обходить обработчик MODX |

События одного запуска объединяются по `trace` и сортируются по полю `ms`. Не публикуйте журналы целиком без проверки на случайные чувствительные данные.

## Безопасность и ограничения

- **Токен в клиентском JavaScript виден посетителям**. Это только временное ограничение доступа к диагностическому приёмнику, **не секрет уровня авторизации**. Используйте случайный одноразовый токен и проводите диагностику короткое время.
- Приёмник проверяет токен и Origin, принимает ограниченный набор полей, пишет диагностику в журнал MODX. Не добавляйте туда значения полей, cookies, токены SendIt, полные query-строки или тела ответов.
- JS записывает временную cookie `fw_trace` (Path=/, Secure, SameSite=Lax), связывающую браузерные и серверные события. **Несколько одновременно открытых вкладок** могут перезаписать её и смешать трассировки.
- `sendBeacon` создаёт отдельные запросы и может немного повлиять на тайминги; наблюдатель старается откладывать их до завершения обычной отправки.
- Не оставляйте трассировщик включённым на рабочем сайте постоянно.

## После расследования

1. Удалите подключение `fw-submit-trace.js` и `FW_TRACE_CONFIG` из шаблона.
2. Установите `fw_debug_enabled = 0`.
3. Отключите или удалите `FWDebugCollector` и `FWLifecycleTrace`.
4. Замените `fw_debug_token`; при необходимости очистите старые диагностические логи.
5. Очистите кэш MODX и проверьте обычную работу формы без наблюдателя.

---

Проект предназначен для **временной диагностики**. Ни клиентский JS, ни серверные плагины не изменяют логику отправки SendIt и не устраняют ошибки автоматически.
